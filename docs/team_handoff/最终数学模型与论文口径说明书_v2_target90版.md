# 最终数学模型与论文口径说明书 v2 target90版

> 这份文件不是提交论文正文，而是给队内统一口径用的说明书。它的作用很简单：让论文手知道怎么写，让检查同学知道重点查哪里，也让我们三个人对“为什么这样建模、为什么这样解释结果”有同一套说法。

## 0. 先说结论

现在模型、代码和结果都已经冻结。论文正文主稿使用 `paper_draft_v2.1_polished.md`，表格使用 `论文核心表格汇总_修正版.md`，代码和结果以 `mcm_c_trip_project_v111.zip` 为准。

最终论文的故事线不是“我们把一个方案调到好看”，而是：

- 问题一先把 10 个景点分层、评分、找联动关系；
- 问题二在无随机扰动下，给出 5 套体验/偏好型行程方案，其中 recommend 是主基准方案；
- 问题三先发现前五套方案在五一强扰动下不稳定，再用诊断实验说明原因；
- 最后构造第 6 套 target90 可靠性优先备用方案，在不改随机参数、不改失败标准的前提下，把整体可靠度做到 0.9458。

一句话：**recommend 是好玩的主方案，target90 是稳妥的兜底方案。二者不是互相替代，而是给不同风险偏好的家庭选择。**

## 2. 三问总逻辑

### 2.1 问题一：先把景点看清楚

问题一不是简单排个喜好分，而是把景点拆成四个维度：

- 喜好度：家人对景点的主观偏好；
- 游览时长：景点本身需要花多少时间；
- 通勤距离：离酒店和其他景点近不近；
- 拥堵敏感度：是否容易受高峰、排队、热门程度影响。

最后得到三层池：

| 层级 | 景点 |
|---|---|
| 高优先级 | A3, A7, A2, A1 |
| 中优先级 | A10, A8, A5 |
| 低优先级 | A9, A6, A4 |

这一步给问题二提供备选基础，避免后面“凭感觉选景点”。

### 2.2 问题二：在无随机扰动下做五套偏好方案

问题二处理的是确定性行程，也就是先不考虑堵车和排队，看看在正常情况下怎样安排最合理。

四个目标是：

| 目标 | 含义 | 方向 |
|---|---|---|
| Z1 | 喜好满意度 | 越大越好 |
| Z2 | 行车负荷 | 越小越好，反向归一化后越大越好 |
| Z3 | 行程紧张度 | 越小越好，反向归一化后越大越好 |
| Z4 | 最小时间缓冲 | 越大越好 |

这里一定要记住：Z2 和 Z3 是成本型目标，但进入综合得分 F 前已经反向归一化，所以最终公式是四项加号。

最终枚举得到 **1,066,932** 个可行解，给出五套方案：

| 方案 | 定位 | 是否为问题二方案 |
|---|---|---|
| recommend | 主基准方案 | 是 |
| preference | 喜好优先 | 是 |
| low_commute | 低通勤优先 | 是 |
| balanced | 喜好与紧凑均衡 | 是 |
| robust | 缓冲优先 | 是 |

recommend 主方案选择 8 个景点：A1, A2, A3, A5, A6, A7, A8, A10，综合得分 F = 0.8770。

### 2.3 问题三：先评估风险，再设计兜底方案

问题三不是直接把问题二方案拿来硬说稳定，而是先诚实评估：在五一强扰动下，它到底稳不稳。

默认强扰动情景假设是：

| 参数 | 数值 | 来源说明 |
|---|---:|---|
| p_peak | 0.6 | 本文默认强扰动情景假设，不是题目给定 |
| p_off | 0.3 | 本文默认强扰动情景假设，不是题目给定 |
| 高峰堵车延时 | U(1,4) | 题目给定的条件延时分布 |
| 平峰堵车延时 | U(0,1.5) | 题目给定的条件延时分布 |
| 高峰排队 | U(0.5,3) | 题目给定 |
| 平峰排队 | U(0,1) | 题目给定 |

注意：题目只给了“发生拥堵时”的延时分布，没有给堵车发生概率。所以 p_peak 和 p_off 必须写成“本文默认强扰动情景假设”，不能写成题目给定。

## 3. v1.1.1 时间边界

这是后面所有模型的基础。论文里必须统一，不要再出现旧口径。

| 天数 | 出发/返店边界 | 解释 |
|---|---|---|
| Day1 | 11:30 后开始景区活动 | 7:00 从家出发 + 4.0h 到酒店 + 0.5h 入住 |
| Day2-Day4 | 08:30 从酒店出发 | 起床、早餐、整装后出发 |
| Day5 | 16:30 前回酒店 | 16:30 回酒店 + 0.5h 离店整备 + 4.0h 返家 = 21:00 前到家 |

这套边界比“每天统一 8:30 出发、21:00 回酒店”更严格，也更符合题意。Day5 只有 8.0 小时景区活动窗口，是后面可靠度低的重要原因。

## 4. recommend 主基准方案

recommend 是问题二的主基准方案。它不是最稳的方案，而是在喜好、行车、紧张度之间比较均衡的体验型方案。

| 日 | 路线 | 出发 | 返店 | 缓冲 |
|---|---|---:|---:|---:|
| Day1 | A2 | 11:30 | 19:06 | 1.90h |
| Day2 | A6 | 08:30 | 15:54 | 5.10h |
| Day3 | A1 -> A5 | 08:30 | 17:24 | 3.60h |
| Day4 | A8 -> A10 | 08:30 | 17:00 | 4.00h |
| Day5 | A3 -> A7 | 08:30 | 15:54 | 0.60h |

最紧的是 Day5。它本来只有 8.0h 上限，recommend 的确定性行程已经用了 7.4h，只剩 0.6h 缓冲。这个数字后面会解释为什么五一扰动下 Day5 很容易失败。

## 5. 为什么前五套方案 R 很低

三套主方案的蒙特卡洛结果如下：

| 方案 | R | P_fail | 说明 |
|---|---:|---:|---|
| recommend | 0.0005 | 0.9995 | 主基准方案 |
| balanced | 0.0005 | 0.9995 | 与 recommend 行程一致 |
| robust | 0.0011 | 0.9989 | 缓冲更大，但仍远低于 0.9 |

这个结果看起来很低，但它不是代码错，也不是确定性行程本身不可行。诊断实验已经说明：

| 场景 | recommend 的 R | 说明 |
|---|---:|---|
| deterministic | 1.0000 | 无扰动时完全可行 |
| road_only | 0.0277 | 只开堵车就已经很低 |
| queue_only | 0.0501 | 只开排队也很低 |
| road_and_queue | 0.0005 | 两类扰动叠加后接近 0 |

通俗地说，就是四个因素叠加：

- 五一强扰动本身很狠；
- 每天有多段路、多次入园，扰动源很多；
- Day3 和 Day5 本来就紧；
- 五天是串联可靠度，只要一天失败，整次行程就失败。

所以低 R 的正确解释是：**前五套偏好方案适合正常体验规划，但在强扰动情景下存在结构性脆弱。**

## 6. Shapley 分解说明什么

Shapley 分解结果是：

| 因素 | 贡献度 |
|---|---:|
| 道路堵车 | 0.5116 |
| 景点排队 | 0.4884 |

这说明道路和排队几乎各占一半。论文里不能说“主要都是堵车造成的”，也不能说“主要都是排队造成的”。更稳的说法是：

> 道路堵车与景点排队贡献接近，说明两类扰动共同侵蚀行程缓冲。可靠性提升必须同时减少出行段数和入园次数。

这句话正好引出 target90。

## 7. target90 是什么

target90 是问题三新增的第 6 套可靠性优先备用方案。它不是问题二主方案，也不替代 recommend。

| 项目 | recommend | target90 |
|---|---|---|
| 定位 | 问题二主基准方案 | 问题三可靠性优先备用方案 |
| 景点数 | 8 个 | 5 个 |
| 每天景点数 | 1-2 个 | 每天 1 个 |
| 目标 | 综合体验更好 | 可靠度达到 90% 以上 |
| 是否参与 Q2 F 排序 | 是 | 否 |
| R | 0.0005 | 0.9458 |

它的核心不是“调参”，而是“换设计哲学”：把景点数降到题目允许下限，每天只安排一个景点，出发时间作为决策变量，减少道路段数和入园次数，把时间转化为可靠性缓冲。

## 8. target90 为什么合法

target90 没有修改这些东西：

| 项目 | 是否修改 |
|---|---|
| p_peak = 0.6 | 否 |
| p_off = 0.3 | 否 |
| 道路延时分布 | 否 |
| 排队分布 | 否 |
| 五天联合可靠度定义 | 否 |
| 失败标准 | 否 |
| Day1 / Day5 边界 | 否 |
| 返程堵车 | 没有漏算 |
| 午餐 1 小时 | 没有漏算 |

它只是用了题目允许的自由度：5-8 个景点、每天 1-2 个景点、合理出发时间。最终选中 A3, A1, A5, A10, A7，得到：

| 指标 | 数值 |
|---|---:|
| R | 0.9458 |
| P_fail | 0.0542 |
| 95% CI | [0.9414, 0.9502] |

target90 的代价也要写清楚：它只玩 5 个景点，覆盖度和舒适体验不如 recommend。但它能给出强扰动下的兜底保障。

## 9. 论文中必须守住的红线

| 不能写 | 应该写 |
|---|---|
| p_peak / p_off 是题目给定 | p_peak / p_off 是本文默认强扰动情景假设 |
| target90 是问题二最终最优方案 | target90 是问题三可靠性优先备用方案 |
| 通过调参达到 90% | 通过方案重设计达到 90% |
| 前五套方案失败，所以模型错了 | 前五套方案在强扰动下存在结构性脆弱 |
| target90 比 recommend 更好 | 两者面向不同决策语境 |
| 道路堵车绝对主导失败 | 道路和排队贡献接近 |
| target90 完美解决问题 | target90 以景点覆盖度和舒适体验为代价换可靠性 |

如果论文手只记一条，就是：**recommend 负责好玩，target90 负责稳。不要把二者混成一个方案。**
